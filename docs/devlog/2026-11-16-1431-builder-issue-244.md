## Summary

- New `game/net/net_messages.gd` (`NetMessages`, `RefCounted`, static functions only):
  `encode_hello`, `encode_input`, `encode_state_hash` and one `decode`.
- Layout, little-endian, type in byte 0. hello: protocol u16, build length u16, UTF-8
  build (at most 255 bytes). input: tick u32, ship u8, thrust and turn as 3 x s32 each,
  one flags byte for the three bools: 31 bytes, about 15 kbps at 60 a second (MP-7).
  state_hash: tick u32, hash s64: 13 bytes.
- `PROTOCOL_VERSION` is 1. `decode` returns either `{"error": ...}` alone or a complete
  message; errors name the problem (empty, unknown type, truncated, oversized, protocol
  mismatch with both versions and the peer's build, thrust outside ±1000, unknown flag
  bits).
- Encoders return an empty array for anything that would not fit (negative or >u32 tick,
  ship index >255, thrust beyond ±1000, build too long).
- `VECTOR_FIELDS` and `BOOL_FIELDS` list the `ShipInput` properties carried; a test
  compares them both ways with `ShipInput`'s script property list.
- `game/core/ship_input.gd` untouched (lane-a).

## Open questions

- Decoding refuses thrust outside ±1000 so a client cannot send more thrust than the
  input range allows; turn is passed through unchecked because the input has no fixed
  turn limit. `ShipState.step` applies whatever turn rate it gets, so before co-op (M5)
  the host should cap a client's turn rate; a decision on that limit belongs to lane-a.
