## Issue

#16 Make Replay.run fail on a rejected frame and reject negative hashes (ARC-1, ARC-2).

## Summary

- `game/core/replay.gd`, `run()`: checks the result of `Sim.step()`. On the first frame
  that does not hold one input per ship it returns `null` and sets the new `run_error`
  to `tick <n>: expected inputs for <ships> ships, found <count>`. A complete run clears
  `run_error`. `error` keeps its meaning (text could not be parsed), so a caller can tell
  a bad file from a replay that was damaged in memory.
- `game/core/replay.gd`, header parsing: a negative `hash` value is rejected with the
  line number. Before, `hash -1` equalled `NO_HASH` and switched the hash check off.
  No `hash` line still means "no expected hash"; `hash 0` is a valid hash.
- `game/tests/test_replay.gd`: four new tests (wrong frame size, short and long;
  `run_error` cleared after repair; negative hash with line number; missing hash line).

The text format, `Sim`, `ShipState` and `basic_flight.replay` are unchanged.

## Open questions

- `run()` now returns `null` on failure, so a caller that writes
  `replay.run().state_hash()` on a damaged replay stops with a script error instead of
  getting a wrong hash. That is loud, as the issue asks, but callers outside tests
  (later: `net/` desync checks) should test for `null` and report `run_error`.
- A frame can also be damaged in memory by holding something that is not a `ShipInput`.
  `run()` does not check that; Godot reports a script error at the typed assignment.
- A `hash` value above the 32-bit range that `Sim.state_hash()` can produce still
  parses. It can never match, so the replay fails its hash check; not rejected at parse.
- Still open: `*.gd.uid` files and `game/openxr_action_map.tres` appear after import and
  were left uncommitted here (#18).
