## Summary

- New `game/core/debris_route_guard.gd` (`DebrisRouteGuard`). `Sim.step` now calls
  `DebrisRouteGuard.advance(self, last_events)` where it called `debris.advance(reactor)`;
  that is the only change to `sim.gd`, which stays at 295 lines. The guard advances the
  debris clock. Then, for each entry falling due on that tick (in file order), it asks
  `KnownRoute.find` with every box explored whether each live ship (hull above zero, not
  escaped) still reaches its exit (its start). The check counts the debris already let fall
  plus this entry. If a ship that has a route now would have none, the entry is marked
  skipped and never becomes solid.
- A ship that already has no route is not counted. Holding debris back cannot give it one,
  and because the guard ran for every earlier entry, debris did not take it away. A literal
  reading ("any ship would have none") would let one stray ship, for example one pushed
  into a too-narrow opening, stop every later cave-in. Open space (no walls) is not checked.
- `MeltdownDebris` gains `skipped` (per entry) and `is_skipped`. `is_solid` is false for a
  skipped entry, so collisions, shots, `OpeningClearance` and `KnownRoute` all follow it.
  `fresh_copy` clears it. `state_hash` adds the held indices only when there are any, so
  every pinned hash stands, G2's included (its placeholder blocks nothing).
- `SimEvent.Kind.DEBRIS_HELD` is appended at the end of the enum, so earlier kinds keep
  their values. `ship` is the first ship that would have lost its route, `magnitude` the
  entry index and `vector` its centre. It is reported before every other event of the tick.

## Open questions

  concern, not this guard's.
- The ship-that-already-has-no-route rule above is my reading of the first criterion; the
  Reviewer may want it stated in the issue.
