## Summary

- **Why the floor (criterion 1).** In Godot 4.7.2's `Main::iteration`, `TIME_PROCESS` is
  timed from the start of `_process` to the end of `RenderingServer.draw`. That span holds
  the render CPU time a second time and the wait for the headset's swapchain image. Only
  `xrWaitFrame` runs before it. The scaler added `TIME_PROCESS` to render CPU and setup.
  On the vsynced Quest (mean frame 8.43 ms at 120 Hz) the CPU input was over `high_water`
  (7.5 ms) on every frame, so the scale fell 1.0 → 0.7 within about 90 frames and stayed.
- New `xr/render_frame_times.gd` (`RenderFrameTimes`). The CPU time is now script
  `_process` time (from `SceneTree.process_frame` to the scaler, which now processes last),
  plus physics, frame setup and the viewport's render CPU. The GPU time is the viewport's
  timestamps, as before.
- New `xr/render_scale_samples.gd` (`RenderScaleSamples`). `RenderScaler.recent` keeps the
  last 600 headset frames: CPU and GPU ms, budget and the scale each frame was drawn at.
- The m6 `render_scale` step now also reports `render_cpu_ms_mean`, `render_gpu_ms_mean`,
  `frame_budget_ms`, `render_scale_min`, `render_scale_mean` and `headset_frames_sampled`
  from that window (in `perf.json` these are the stress scene's last frames). It fails when
  every frame sat at the floor while both means were under `high_water` of the budget.
  Off the headset it samples nothing and says so.
- **Criterion 4.** The runner flies one tick per frame. At 120 Hz the 3,000-tick replay ends
  after about 25.3 s, but the step measures for 32 s. The scene then flies on for
  ≈ 403 ticks. The fix is in `suites/m1.json` (lane-a), so it went to #1528 (`triage`).
- **Criterion 5.** The device report has no CPU/GPU split, so there are no glass numbers
  yet. The next device run's `render_scale` step will show the GPU time.
