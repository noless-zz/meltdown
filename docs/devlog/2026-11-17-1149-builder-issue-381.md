## Cause (found; it is in core, so this run stops as the issue says)

The 90-tick G2 `for_level` flight from #340 was run in this sandbox (Intel Xeon, glibc 2.39)
and on CI (GitHub `ubuntu-latest`), with Godot 4.7.2 on both. Temporary diagnostic commits on
this branch printed a breakdown on CI.

- **Same on both machines:** the weapon listing (already sorted:
  `arc_lance, needle_gun, pulse_cannon, slug_thrower`), every part's `values_hash`, the
  tick-0 session hash (4279815811), and the ship's hash on every tick through 90
  (2896393452 at tick 90).
- **Different:** robot 0's orientation after tick 1, in the last bit. Replaying its first
  `turn_towards` step by step showed identical inputs (target, offset, distance, `to_target`,
  facing, cross-product axis), and then `facing.angle_to(to_target)` returned **0.06978795**
  here and **0.06978794** on CI. GDScript's double `atan2` of the same two values gave
  0.06978794517499533 on both. That value lies 0.44 of the way from one float
  (0.069787942, CI's answer, the nearer one) to the next (0.069787949, this sandbox's
  answer). So the engine's float `atan2` (`Vector3.angle_to` calls glibc `atan2f`, linked
  dynamically) is off by one bit on one machine and not on the other. Everything after that follows from the different turn
  angle. By tick 90, 4 of the 6 robots differ, and so does the whole-sim hash
  (818969652 here, 2263984340 on CI).
- **Not the cause:** directory listing order. The pinned replay files match because none of
  them has a robot turning at a near-tie angle like this one.
- `angle_to` is used in `game/core/robot_state.gd` (`turn_towards`, `fire_at`) and in
  `game/net/bot_pilot.gd` (the bot's fire cone). The fix belongs to core, so per the issue
  it is left to the Planner. A machine-independent turn could compute the angle in double
  precision with GDScript's `atan2` and snap it to float, or avoid the angle and build the
  rotation from the clamped cross and dot products directly. It still has to be pinned on
  CI.

## Summary of the change

- `SpawnLoader.load_parts` now goes through `parts_from_files(weapon_dir, names)`, which
  sorts the names first. Listing order was not the cause here, but the catalogue's order
  should not depend on it, and the issue's two-orders test needs the helper.
- New `game/tests/test_session_start_determinism.gd` (4 tests): G2's session start is pinned
  (4279815811), and so is its ship after the #340 flight (2896393452). Both values were
  measured on both machines. The catalogue is built from the weapon files in two orders and
  gives the same keys in id order, the same parts and the same 90-tick session hash.
  `load_parts` gives the same catalogue as the helper. The whole-sim G2 flight hash is
  **not** pinned (criterion 2), because it fails on CI until the core fix lands.
