## Issue

#913 (M3, MAP-1, MAP-2, RUN-2, MP-2, DEV-7): the reactor was missing from the held map
once found, and the solid exit cube hid the tunnel beside it.

## Summary

- Cause confirmed as the Planner read it: `MapWiring` marked the reactor only after the
  ship had been inside a box holding the reactor's centre.
- `MapWiring`: the reactor is known from the first frame the ship has been in its box
  or has a clear line to its centre (`LineOfSight.clear` over the replay's copy of the
  walls), and always once destroyed. It stays known. Destroyed comes from the new
  `MapRouteWiring.reactor_destroyed` (a `SessionSnapshots` copy), because a pinned test
  forbids `sim.` in `map_wiring.gd`. `meltdown_running` now uses it as well.
- `MapShapes.exit_cube`: same edge (`2 * exit_radius_m`), unshaded, alpha `exit_alpha`,
  no depth writes, both faces. `MapShapes.reactor_ball`: `reactor_dead_color` once
  destroyed, no depth test and render priority 1 (the exit's is 0), so it draws over the cube.
- `map_look.json`/`MapLook`: optional `reactor_dead_color` (shipped 0.45, 0.12, 0.35) and
  `exit_alpha` (0.05..1, shipped 0.35).
- `MapHologram.set_markers` takes an optional `reactor_destroyed`; `marker_nodes()` added
  for tests. The `parse_look` wrapper went, so the file stays under 300 lines.
- New acceptance check `map_markers` (`acceptance_map_markers_check.gd`), registered in
  `AcceptanceStep`, the parser and `AcceptanceChecks`. `m3.json` untouched: #912 (lane-a)
  is still open, so #912 adds the check to the four generated steps.
