## Summary

- New `game/data/components/` with four original kinds, one file each: `scrap_alloy`
  (tier 1), `cell_salts` (tier 1), `circuit_shards` (tier 2), `core_glass` (tier 3). Keys
  `id`, `display_name`, `tier` (whole number 1 to 3) and `map_colour` (`"#rrggbb"`, kept as
  text because core never touches rendering).
- `core/component_def.gd` parses one kind; every key required, unknown keys rejected, each
  error names the key. `core/component_list.gd` loads all kinds from texts keyed by file
  name (core opens no files), prefixes each error with the file name, rejects a duplicate
  `id`, and sorts kinds by id so order never depends on the caller.
- `core/component_drop.gd` parses one drop-table line `{"id", "chance", "count": [min, max]}`
  (chance above 0 and at most 1; counts whole, 1 to 99, min <= max; a kind listed twice is
  an error). It is its own file so `robot_def.gd` stays well under 300 lines (now 274).
- `RobotDef` reads the optional `components` key; no key means no drops.
  `parse_json(text, kinds)` rejects an unknown component id when given the kind list, and
  `check_components(kinds)` does the same for callers that parsed without it (the existing
  spawn and level loaders, which do not need drops yet).
- The six shipped robots have tables: tier 1 on all; tier 2 (`circuit_shards`, 10 % and
  15 %) only on `hauler` and `warden`; no tier 3 yet.
- No simulation change: the table stays out of `RobotDef.values_hash`, so replay and suite
  hashes are unchanged. It should join the hash in the issue that makes robots drop.
