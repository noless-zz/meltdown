## Summary

Tests only; no code change was needed.

- New `tests/test_main_headset_off_meltdown.gd` (2 tests). The real main scene on G2, rig built
  and `_ready` run, ship in the reactor's room, reactor destroyed, half a second into the
  meltdown. For three orders the runtime can report a removed headset (focus lost; focus lost then
  stopping; loss pending then stopping), five seconds of 72 Hz frames, 300 one-second frames and
  one 300 s frame (G2's longest countdown is 120 s): the tick, the countdown ticks, the panel's
  countdown, the hull, the state hash and the shots in flight do not change. Back on (visible,
  then focus) the first frame runs at most one tick, the run is still going, and the countdown
  runs again. The second test: after any pausing call the very next frame runs no tick.
- A mutation check (making `on_session_visible` not pause) fails both tests: 1805 ticks ran.

## Findings

- The pause holds in the main scene. The window in which fire, debris or robots could still take
  the hull is zero ticks of ours after the runtime's call; what remains is the runtime's own delay
  in reporting the headset off, which only a headset can measure.
- The flat keyboard build has no pause: a desktop window losing focus keeps flying.
- In this G2 setup a ship left at the start escapes as soon as the meltdown starts (its exit
  sphere). That is not this bug but explains why the test moves the ship first.
