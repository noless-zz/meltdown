## Issue

## Summary

- `xr/render_scale_controller.gd` (`RenderScaleController`, pure `RefCounted`): fed each frame's
  CPU and GPU time and the refresh rate, it answers the scale. The longer of the two times is
  compared with one refresh interval. `frames_down` frames in a row over `high_water` step it
  down; `frames_up` frames in a row under `low_water` step it up. It stays within floor and
  ceiling (never above 1.0) and changes at most once per `interval_frames`. Off means always 1.0.
- `xr/render_scale.json` and `xr/render_scale_table.gd` (`RenderScaleTable`). Shipped values:
  floor 0.7, ceiling 1.0, step 0.1, high 0.9, low 0.7, 5 frames down, 45 up, 30 frames between
  changes. A missing, mistyped or out-of-range value is refused with the field named. A refused
  file turns scaling off.
- `xr/render_scaler.gd` (`RenderScaler`): a node the rig adds in `build()`. Only while the
  viewport renders to the headset (`use_xr`) does it measure the viewport's render times and set
  `Viewport.scaling_3d_scale`. It does not use `OpenXRInterface.render_target_size_multiplier`,
  because that sizes the swapchain at session start and does not follow later changes. In the
  flat build it does nothing.
- Dev menu: a read-only "Render scale: 85%" row in the Display section (`DevMenuRenderScale`,
  `DevMenuValueRenderScale`). Like every value row, confirming returns `render_scale:<percent>`,
  which its helper takes and ignores.
- `AcceptanceFrameBudgetCheck` samples `RenderScaler.in_use` on the frames it times
  (`AcceptanceRenderScaleStats`). So the m6 `stress_scene` step reports the scale's minimum,
  mean and frames below 1.0 beside its frame times. The scale is reported only, never judged.
- New m6 perf step `render_scale` (`acceptance/checks/render_scale_check.gd`): on the shipped
  table, 600 slow frames and then fast ones take the scale to the 0.7 floor and back to 1.0.
- `main.gd` is untouched (it is at 300 lines and #1424 edits it).
