## Summary

- New `game/core/stable_angle.gd` (`StableAngle.between(a, b)`): the float cross product's
  length and the float dot product, as `Vector3.angle_to` uses, then GDScript's double `atan2`
  rounded once to float. Zero-length inputs give 0. Where the platform's `atan2f` already
  rounded correctly the result is the same as before, so recorded hashes stand.
- `RobotState.turn_towards`, `RobotState.fire_at` and `BotPilot`'s fire cone use it instead of
  `angle_to`.

## Other float trigonometry feeding simulation state

Searched `core/` and `gen/` (and `bot_pilot.gd`) for `angle_to`, `signed_angle_to`, `slerp`,
`Quaternion`, `atan`, `acos`, `asin`, `sin`, `cos`, `rotated` and `Basis(axis, angle)`. No
other `angle_to` in `core/`, `gen/` or `net/`; `gen/` has no trigonometry at all.

- `ShipState` turning: `Basis.rotated` three times a tick (`sinf`/`cosf`). Left alone as the
  issue says; it matched for 90 ticks on both machines and the ship hash is pinned. It could in
  principle differ on a libm whose `sinf`/`cosf` round differently.
- `RobotState.turn_towards`: `Basis(axis, turn)` (same `sinf`/`cosf` path). Same judgement;
  the whole-flight pin now covers it on CI.
- `orthonormalized`, `normalized`, `length`, `Basis.looking_at` (`RobotSpawn`): only `+ - * /`
  and `sqrt`, which IEEE rounds exactly, so they cannot differ.
- `BotPilot` steering errors: GDScript `atan2` (double) of float inputs, then turned into a
  quantized `ShipInput`. Double `atan2` matched on both machines for the near-tie; low risk.
- `xr/label_fade.gd` uses `angle_to` for label fading only, outside the simulation.
