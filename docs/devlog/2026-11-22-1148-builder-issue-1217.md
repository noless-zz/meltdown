## Summary

- `SalvageRules.drop_delay_ticks`: optional key of `data/salvage.json`, a whole number
  0..600; shipped as 45 (0.75 s at 60 Hz). A file or replay salvage line without the
  key reads as 0, and 0 is neither written to the line nor hashed, so older replays
  parse and fly unchanged.
- `SalvageItem.pickup_delay`: set from the rules when a robot drops its part
  (`RobotTick.remove_destroyed`, one line outside the issue's file list), counted
  down at the start of `SalvagePickup.collect`; while above 0 no ship takes or pulls
  the part. It still drifts. Hashed only while above 0. Swapped-out parts get no
  delay and keep `ignored_ship`.
- `test_salvage_drop_delay.gd`: not taken before tick N, taken on tick N; N = 0 is
  today's behaviour; a delayed part drifts but is not pulled; same seed and inputs
  give the same hash; the key is optional, whole and bounded, and survives the replay
  line. `test_main_salvage` now flies the delay before expecting the pull.
