## Summary

- New `acceptance/acceptance_frame_hook.gd` (`AcceptanceFrameHook`): a check asks for "the next
  drawn frame" with a callback. It listens to `RenderingServer.frame_post_draw` (no forced draw,
  unsafe under OpenXR). Headless or on the dummy renderer the callback comes on the next frame
  with `drawn` false. Cleanups registered with `on_end` run when the step ends or times out.
- Check files may now declare `static func frame_work() -> Dictionary[String, Callable]`
  (`AcceptanceCheckFiles`), only for their own checks. `AcceptanceChecks.still_waits` starts the
  frame work once the step's replay, samplers and headset waits are done, and keeps the step
  open while a frame is awaited. The runner's step-readiness tail moved there in one line, so the
  runner stays under its 260-line test limit; the step time limit of #1444 still applies.
- `LevelLoadTiming` now has `begin` (builds the load under a parent in the scene, up to the first
  tick) and `finish` (adds `first_frame_s`, `total_s` and `drawn`, takes the load out). `measure`
  is both with no frame. `first_frame_s` is the fourth phase.
- New `acceptance/level_load_frames.gd` (`LevelLoadFrames`): the `level_load` check's frame work.
  It loads each planned level into the game scene, one per drawn frame, then compares the
  unmeasured hash as before.
- `checks/level_load_check.gd`: the judge reads the frame work's timings. Where no frame was
  really drawn it reports "skipped" with the times (decision record 0005); over budget still fails.
- The m6 `perf` part's `level_load` step file is unchanged: the step names the same checks, and
  the check now waits for the frame. Its default 120 s time limit covers four loads at the 8 s budget.

## Test results

  `test_acceptance_checks.gd` and `test_acceptance_time_limit.gd` pass. The full suite is in the

  8 s budget there, as expected for a software renderer. It shows that the compile is now counted.
