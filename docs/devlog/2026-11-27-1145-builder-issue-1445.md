## Summary

- `acceptance/checks/level_load_check.gd`: the `level_load` check. For each load in the plan it
  times the load, builds the same level again without the clock, and requires the same state
  hash after the first tick (ARC-1). It then judges the worst `total_s` against the budget.
  When it fails, it names the level (run, depth, seed) and its slowest phase.
- `acceptance/level_load_timing.gd`: times one load in three phases. `generate_s` covers
  `LevelSwitch.load_level`, which is the generator plus the validators. `build_view_s` covers
  the session with its robots, the shaft's run rules (components, miners, alarm), the level view
  with the ambient bake, and the lights. `first_tick_s` covers the first tick. These are the
  same steps as `LevelStart.level_session`. The wall clock is read only in `acceptance/`.
- `acceptance/level_load_plan.gd` and `acceptance/checks/level_load.json` (ARC-4): the budget is
  8.0 s. The plan loads runs 4, 8 and 12, each at its deepest level (level 5, the longest run
  `run.json` allows) through the `deep` shaft (robots x1.3), plus the stress level. A run seed
  whose plan is shorter than the longest run is refused.
- `suites/m6/perf.json`: new step `level_load`.

## Deviations from the issue, said in the PR

- The budget is in the check's data file, not a step key. A step key would edit
  `AcceptanceStepParser`'s key list, and #1444 (lane-a) is changing those same lines.
- "To the first frame flown" is measured to the first simulation tick. Judges run
  synchronously, and check files have no frame hook. Forcing a draw would be unsafe under
  OpenXR, and adding a hook would mean editing `acceptance_runner.gd`, which #1444 owns. So
  the GPU's first draw (shader compiles) is not in the number. Follow-up: #1480 (`triage`).
