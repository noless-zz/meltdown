## Issue

#589 (playtest, M1, DEV-8): the first install of a session fails because the headset drops
off adb for a moment after being plugged in or woken, and the immediate retry lands in that
gap with `device '<serial>' not found`.

## Summary

- `tools/update_quest.sh` and `tools/update_quest.ps1`:
  - New named values at the top: `device_wait_seconds` / `$deviceWaitSeconds` (20 s,
    overridable with `MELTDOWN_DEVICE_WAIT_SECONDS`) and `install_retries` /
    `$installRetries` (2).
  - Before the first install on each headset: `adb -s <serial> wait-for-device`, bounded by
    that time (a background process in bash, since macOS has no `timeout`; a
    `System.Diagnostics.Process` with `WaitForExit` in PowerShell), then
    `adb -s <serial> shell true`.
  - A failure with no reason, `not found` or `offline` waits for the headset again before
    each retry and retries at most twice (still `--no-streaming`, as in #210). A failure
    with a `Failure [...]` reason is still not retried.
  - `not found` / `offline`, or a headset that does not come back in time, is reported as
    "the headset dropped off USB for a moment" instead of "adb gave no reason"; the by-hand
    command and kept download stay as in #210.
- `tools/fixtures/update_quest/bin/adb`: `wait-for-device` (returns at once, or hangs with
  `STUB_ADB_WAIT=hang`) and `STUB_ADB_SEQUENCE` to script install attempts
  (`blank`, `notfound`, `offline`, `ok`).
- `tools/test_update_quest.sh`: five new checks (wait, wake, install order; blank →
  not found → success; stays not found; stays offline; bounded wait). The #210 blank check
  now expects two `--no-streaming` retries instead of one, because #589 raises the retry
  count to two.
- `tools/device_acceptance.ps1` is untouched: it belongs to #230 (lane-b) and is left to a
  follow-up, as the Planner scoped.
